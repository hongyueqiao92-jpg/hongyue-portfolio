01 / 项目概览

UP Agent

把业务意图转成可执行、可检查的人群方案

面向营销运营的智能圈选设计：让用户从业务目标开始，由系统组织规则与执行，人保留结果检查、修正与提交的决定权。

一期结果界面将执行反馈与结构化人群结果并排呈现，方便用户同时检查过程与产出。

项目阶段

一期已上线；二期为后续界面框架探索。

一期交付

目标输入 → 过程反馈 → 结果检查 → 人工提交

我的职责

用户访谈、交互与视觉设计、方案调整及前端 Coding 协作。

核心用户为营销运营，同时面向产品经理和数据分析师。一期围绕圈选方案生成、检查、修改和人工提交展开，下游投放在外部平台完成。

06 / 核心设计决策与方案落地

先保障任务可执行、结果可判断，再完善规则解释

沿用第05章的检查问题：入口能否启动、结果能否判断、规则能否调整。以下分别说明方案取舍与交互设计。

01 / 容易开始：启动条件

把必要条件放在启动前

一期任务不能在执行中暂停等待用户补充必要范围，因此将圈选 ID 体系和必要的人群范围确认前置到首页。

模板和输入提示帮助用户描述目标；具备执行所需条件后，先生成候选方案，再基于具体结果检查和修改。

02 / 结果可判断：信息取舍

卡片先提供判断依据，完整条件进入详情核对

上线前调研形成了信息优先级：先看人数，再看人群质量，最后检查具体规则。在有限的上线周期内，产品优先验证核心圈选能力，研发也难以完成可靠的完整规则转译。

原计划

业务概述与层级规则同时放在卡片内。

调整后

保留规则摘要并增加画像，完整条件在详情中核对。

两版都有规模、活跃和交易指标。调整的重点是减少卡片里的复杂规则层级，增加画像信息；短规则摘要保留线索，完整条件交给详情。

我参与结果展示和规则编辑方案调整，在产品优先级与研发约束下，优先保留可判断、可检查的核心体验，将可靠的完整规则自然语言转译延后。

让用户看到数据时，也能理解指标含义

  1. 用户反馈

    上线前，用户关注活跃度、活跃占比等关键数据，但对数据口径缺少理解。

  2. 问题判断

    仅展示数值不足以帮助用户正确理解数据，需要让指标含义在查看时可解释。

  3. 设计调整

    在关键数据旁增加口径与指标解释说明，供用户查看数据时参考。

07 / AI执行机制、技术约束与异常处理

执行反馈按实际返回内容流式呈现，不预设完整阶段文案

设计原本希望把工作流整理成稳定的关键阶段，但 执行系统返回内容存在不确定性，无法稳定填充预设阶段说明。调整后保留过程节点，具体反馈随实际返回逐步呈现。

启动条件前置，执行反馈随实际返回，结果交由人检查

  1. 确认必要范围

    圈选 ID 体系与人群范围在启动前确认。

    对应06启动条件
  2. 固定工作流执行

    衔接规则提交与圈选计算。

    终止后不可原位恢复
  3. 按实际返回呈现

    保留过程节点，逐步展示反馈。

    反馈与异常的表达边界
  4. 人工检查结果

    核对规模、规则与画像，再决定修改或使用。

    返回06修改与确认

检查后需要调整 → 按第06章的规则影响范围选择处理路径。

原设计目标

阶段化解释任务

预先组织用户能理解的关键步骤与对应说明。

落地限制

返回内容决定反馈

运行中的信息不足以稳定填充每个预设阶段。

上线调整

随返回内容流式展示

保留可识别的过程节点，具体内容按实际返回逐步呈现。

一期采用固定工作流，不支持自主任务编排。设计能说明执行进展，但不能承诺系统尚不具备的恢复和处理能力。

终止，不是暂停

用户只能终止，不能从终止位置恢复；一期没有自主任务编排。

反馈，不是完整推理

任务执行文案不等于模型内部推理；不将界面中的算法说明等同于已经验证的技术实现。

提示边界，不冒充修复

缺标签、暂无数据和接口异常需要分别说明，不能用同一种等待状态掩盖差异。一期没有自动诊断、修复或恢复闭环。

上线后用户反馈

一期上线后，我与产品沟通确定研究对象，负责约访、访谈内容、访谈执行及整理总结。自然语言帮助开始任务，但仍有人工核查、卡片关注有限、标签映射与提交打断等问题。

画布表达的初版测试和上线后反馈见第05章；这里重点保留后续问题，不将定性评价外推为总体满意度或效率提升。

从反馈与交付中沉淀三条判断

  1. 保留人对结果的判断。AI 提供候选，结构化规则让人能够检查、修改并确认使用。
  2. 按真实能力组织反馈。执行说明服从实际返回，不能靠界面承诺自主编排或异常自愈。
  3. 把对齐放在编码之前。明确实现边界和合并方式，再投入界面还原，减少无效修改。

二期补充探索了持续分析与多能力工作区框架；这里只记录阶段方向，不将二期方案算作一期交付，也不扩展为本人主导后续实现。
